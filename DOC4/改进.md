# SPM 指定模块改进建议

## 说明

- 评审范围：
  - `src/ltsensor/spm_apd`
  - `src/ltsensor/spm_ec`
  - `src/spmci`
  - `src/ltsensor/spm_sensor.c`
- 结论来自静态代码审查，未结合运行时验证。
- 文中 `潜在缺陷风险` 表示“代码形态上存在明显风险或疑似拷贝偏差”，建议结合板级联调或回归测试确认。

## 1. `src/ltsensor/spm_apd`

### 总体判断

`apd_sensor.c` 与 `apd_sensor_dual.c` 明显是同源分叉后的两套实现，核心流程包含大量重复代码，只在少量常量、通道数和公式细节上不同。这类结构短期可用，但后续任何小改动都很容易出现“修了一边漏另一边”的维护问题。

### 优化建议

#### 1.1 抽取普通版与 Dual 版共享骨架

- 问题：
  `GetApdSensor()`、`SetChannelPara()`、固定参数读取、EEPROM 解析、打开设备和数据处理骨架在普通版和 dual 版中高度重复，仅少量常量和公式不同。
- 影响：
  重复逻辑扩大维护面，后续修复和新增特性极易出现版本分叉。
- 建议：
  抽出一个共享的 APD 公共层，保留“版本描述符”或“策略表”来承载差异项，例如：
  - WSEC 通道数
  - EEPROM 步长
  - WSEC/EC 的 PAC/PDC 公式差异
  - 电阻常量、偏压/温度换算系数
- 涉及位置：
  - `src/ltsensor/spm_apd/apd_sensor.c:31-218`
  - `src/ltsensor/spm_apd/apd_sensor_dual.c:33-260`
- 优先级：高

#### 1.2 将版本差异从“散落宏 + 分叉函数”收敛成显式描述

- 问题：
  目前 dual 版差异散落在 `apd_sensor_dual.h` 和 `apd_sensor_dual.c` 中，例如 `APD_WSEC_DUAL_MAX_CHANNEL_NUM`、`WSEC_APD_DUAL_DATA_NUM_PER_CHANNEL`、`APD_R_VD`、不同温度/偏压换算公式等。
- 影响：
  阅读者需要在头文件和实现文件之间来回跳转，才能拼出“V3/V5 到底差了什么”。
- 建议：
  引入 `ApdVariantDesc` 一类的描述结构，集中承载：
  - 通道数
  - EEPROM 步长
  - WSEC 电阻/换算系数
  - 公式函数指针
  这样普通版和 dual 版只保留一套流程代码。
- 涉及位置：
  - `src/ltsensor/spm_apd/apd_sensor.h:19-83`
  - `src/ltsensor/spm_apd/apd_sensor_dual.h:19-79`
  - `src/ltsensor/spm_apd/apd_sensor.c:54-118`
  - `src/ltsensor/spm_apd/apd_sensor_dual.c:58-143`
- 优先级：中

#### 1.3 不要忽略 `memcpy_s()` 返回值

- 问题：
  多处 `memcpy_s()` 直接强转为 `(VOID)`，失败时不会中断流程，也不会向上返回错误。
- 影响：
  一旦参数长度、目标大小或数据布局与预期不一致，代码会继续运行，排障成本很高。
- 建议：
  为 EEPROM 解析和固定参数缓存写入增加统一的安全拷贝辅助函数，强制检查返回值，并返回统一错误码。
- 涉及位置：
  - `src/ltsensor/spm_apd/apd_sensor.c:130-149`
  - `src/ltsensor/spm_apd/apd_sensor.c:182-183`
  - `src/ltsensor/spm_apd/apd_sensor_dual.c:155-174`
  - `src/ltsensor/spm_apd/apd_sensor_dual.c:207-208`
- 优先级：高

#### 1.4 让公式计算函数更适合单测

- 问题：
  `CalculateWsecApdPac()`、`CalculateEcApdPac()`、`CalculateEcApdPdc()` 等函数本身是纯计算，但当前和设备访问、EEPROM 流程处在同一大文件中。
- 影响：
  数学公式、边界条件和版本差异难以独立验证。
- 建议：
  将纯计算函数迁入独立模块，配合表驱动单测覆盖：
  - `gTia == 0`
  - `gVga * gTia < __DBL_EPSILON__`
  - dual / 非 dual 的电阻与公式差异
  - EEPROM 参数缺失或全零
- 涉及位置：
  - `src/ltsensor/spm_apd/apd_sensor.c:54-118`
  - `src/ltsensor/spm_apd/apd_sensor_dual.c:58-139`
- 优先级：中

### 潜在缺陷风险

#### 1.5 Dual 版 WSR 分支疑似沿用了左侧 OEB 设备范围

- 问题：
  `SPM_SENSOR_APD_WSR` 分支中，`channelId` 使用了右侧枚举，但 EEPROM 读取仍传入 `APD_SENSOR_SPM_WSECL_OEB_EEP` 和 `APD_SENSOR_WSECL_MAX`。
- 影响：
  这是典型的复制粘贴偏差形态，可能导致右侧 APD 读取左侧设备配置，或至少让后续维护者误判真实映射关系。
- 建议：
  优先核对设备枚举和右侧 OEB EEPROM 范围；如果当前行为正确，也建议把左右侧差异改成显式表驱动，避免后续再误改。
- 涉及位置：
  - `src/ltsensor/spm_apd/apd_sensor_dual.c:340-342`
- 优先级：高

#### 1.6 Dual 版 WSEC 标定数据写入缺少边界保护

- 问题：
  `SaveApdE2pCalibrationData()` 在 dual 分支里按 `WSEC_APD_DUAL_DATA_NUM_PER_CHANNEL` 递增 `eepIndex`，但没有像普通版那样结合 EEPROM 上限做循环边界保护。
- 影响：
  当前数据布局若发生调整，可能出现越界读取或静默脏数据写入。
- 建议：
  增加显式上限校验，例如检查 `eepIndex + WSEC_APD_K_INDEX_OFFSET < paraLen`，并将 `paraLen` 作为函数参数传入。
- 涉及位置：
  - `src/ltsensor/spm_apd/apd_sensor.c:192-215`
  - `src/ltsensor/spm_apd/apd_sensor_dual.c:217-239`
- 优先级：高

## 2. `src/ltsensor/spm_ec`

### 总体判断

`spm_ec` 模块已经有一定表驱动意识，但“元数据表”和“流程代码”仍然没有完全收敛：WSEC/RAEC、普通版/dual 版在标定读取、寄存器下发、设备查找和状态管理上仍保留了多套近似实现。当前结构可工作，但扩展新版本或修复校准逻辑时，修改成本偏高。

### 优化建议

#### 2.1 收敛轴参数表的硬编码

- 问题：
  `AxisParaInfo` 大表在左右台、RSEC/LRA/ARA、dual/non-dual 间存在大量规则性重复，差异主要是设备名前缀、起始行和数据宽度。
- 影响：
  新增硬件版本时需要手工维护多张长表，出错概率高，也不利于审查。
- 建议：
  用宏、构造函数或静态生成脚本收敛这类表项，至少把“左右台仅设备名前缀不同”的部分生成化。
- 涉及位置：
  - `src/ltsensor/spm_ec/spm_sensor_ec.c:32-125`
  - `src/ltsensor/spm_ec/sensor_ec_dual.c:28-82`
- 优先级：中

#### 2.2 合并普通版与 Dual 版的标定下发流程

- 问题：
  `EcWriteCalibParam()` / `EcWriteCalibParamDual()` 以及其下游写寄存器流程结构近似，都是“按轴类型选择参数切片，然后查设备句柄并写入 FPGA”。
- 影响：
  任何对错误处理、日志、写入顺序的改动，都需要在两套实现中重复维护。
- 建议：
  将公共流程抽成统一入口，把差异封装到“轴类型处理器”或“版本策略”中，仅保留差异化的参数映射函数。
- 涉及位置：
  - `src/ltsensor/spm_ec/spm_sensor_ec.c:131-389`
  - `src/ltsensor/spm_ec/spm_sensor_ec.c:391-430`
  - `src/ltsensor/spm_ec/sensor_ec_dual.c:181-304`
- 优先级：高

#### 2.3 为设备句柄建立直接索引，避免反复线性查找

- 问题：
  `EcReadCommonProc()` 和 `EcWriteCommonProc()` 每次都先通过 `cfgItemId` 找设备，再通过设备名线性扫描 `handleArr` 找句柄。
- 影响：
  逻辑路径偏长，读写热点路径里存在重复查找和重复错误处理。
- 建议：
  在 `EcOpenDev()` 初始化阶段直接建立：
  - `cfgItemId -> handle`
  - `devName -> handle`
  - `eepromSensorId -> sensorDev`
  等缓存映射，至少把热点路径的二次线性查找去掉。
- 涉及位置：
  - `src/ltsensor/spm_ec/sensor_ec_common.c:70-137`
  - `src/ltsensor/spm_ec/sensor_ec_common.c:258-296`
- 优先级：中

#### 2.4 统一“写寄存器 + 记录日志 + 处理错误”的样板代码

- 问题：
  `EcWriteOebRefMiscQuantParam()`、`EcWriteOebMeaQuantParam()`、`EcWriteRefMiscQuantParam()`、`EcWriteMeaQuantParam()`、`EcWriteRefParamDual()`、`EcWriteMeaParamDual()` 都在重复执行“拿 handle -> 写数组 -> 打日志 -> 返回错误”的流程。
- 影响：
  错误码、日志格式、超时参数和后续修复策略不容易保持一致。
- 建议：
  提炼统一的写设备辅助函数，把差异保留在“参数装配”阶段。
- 涉及位置：
  - `src/ltsensor/spm_ec/spm_sensor_ec.c:131-357`
  - `src/ltsensor/spm_ec/sensor_ec_dual.c:184-238`
- 优先级：中

### 潜在缺陷风险

#### 2.5 `g_wsecConfigPg` 是跨实例的全局运行态

- 问题：
  `g_wsecConfigPg` 在文件级全局保存主从 PG 状态，由 `RaecSetEngStatus()` 写入，在 `EcSensorReadMiscData()` 中读取并决定使用哪个 DMA 句柄。
- 影响：
  这会把“某一次配置动作的结果”扩散到整个进程级 EC 读数路径；一旦存在多实例、多传感器交错配置，状态可能互相污染。
- 建议：
  将该状态下沉到 `EcMng`，并明确它的作用域是“单个 sensor 实例”还是“单个读头组”。
- 涉及位置：
  - `src/ltsensor/spm_ec/spm_sensor_ec.c:30`
  - `src/ltsensor/spm_ec/spm_sensor_ec.c:436-463`
  - `src/ltsensor/spm_ec/spm_sensor_ec.c:1173-1202`
- 优先级：高

#### 2.6 Dual 版标定元数据里存在空 `optDevice`

- 问题：
  dual 版 `AxisParaInfo` 表中 `optDevice` 全部为空字符串，当前流程虽然没有直接使用它，但字段语义已经与普通版明显偏离。
- 影响：
  后续如果公共逻辑误把 dual 版也接到 `optDevice` 相关流程，容易在运行时才暴露问题。
- 建议：
  若 dual 版确实不需要该字段，应拆分结构体或显式标注“该版本不使用该字段”，避免共享结构承载无效数据。
- 涉及位置：
  - `src/ltsensor/spm_ec/sensor_ec_dual.c:29-67`
- 优先级：中

## 3. `src/spmci`

### 总体判断

`spmci` 代码量不大，但承担了版本选择的关键入口。当前实现能工作，但接口设计和执行成本都还有收缩空间，尤其是参数池访问策略会直接影响 `spm_sensor.c` 初始化路径。

### 优化建议

#### 3.1 避免每次匹配都重复创建/销毁参数池

- 问题：
  `SPM_SensorCheckCI()` 每次调用都会执行一次 `LTR_CreatePb()` 和 `LTR_DestroyPb()`，而 `SPM_SensorCheckCIAndCalc()` / `SPM_SensorCheckCIOrCalc()` 又会循环多次调用它。
- 影响：
  初始化期间会产生重复开销和重复日志，也把“条件计算”与“资源生命周期”耦合在一起。
- 建议：
  将参数池句柄上提到调用方，或提供一次性批量查询接口，避免在布尔表达式求值时不断重复打开资源。
- 涉及位置：
  - `src/spmci/spm_ctrl_item.c:23-57`
  - `src/spmci/spm_ctrl_item.c:60-103`
  - `src/ltsensor/spm_sensor.c:161-180`
- 优先级：高

#### 3.2 收紧接口签名，补齐 `const` 约束

- 问题：
  `key`、`value`、`conditions` 都是只读输入，但头文件和实现都没有加 `const`。
- 影响：
  接口语义不清晰，也不利于编译器帮助发现误用。
- 建议：
  至少收紧为：
  - `const CHAR *key`
  - `const CHAR *value`
  - `const HCS_KeyMapItem *conditions`
- 涉及位置：
  - `src/spmci/spm_ctrl_item.h:38-46`
  - `src/spmci/spm_ctrl_item.c:23-103`
- 优先级：低

#### 3.3 合并 `And/Or` 两个求值骨架

- 问题：
  `SPM_SensorCheckCIAndCalc()` 和 `SPM_SensorCheckCIOrCalc()` 主体循环几乎一致，只是短路条件不同。
- 影响：
  维护上是两份几乎相同的代码，新增统计、日志或容错逻辑时需要双改。
- 建议：
  抽出一个内部通用函数，通过“初始值 + 短路条件 + 合并规则”驱动 `AND/OR` 计算。
- 涉及位置：
  - `src/spmci/spm_ctrl_item.c:60-103`
- 优先级：低

### 潜在缺陷风险

#### 3.4 “控制项不存在”被当成硬错误，可能阻断默认兜底

- 问题：
  `LTR_QryParaFromPb()` 查不到控制项时，`SPM_SensorCheckCI()` 直接返回 `HELF_ENOTSUPPORT`；而 `SPM_SensorQryCtrlItemFuncSet()` 遇到该错误会直接返回，不会继续尝试默认映射项。
- 影响：
  当环境缺少控制项时，系统不是“匹配失败后走默认项”，而是直接初始化失败。
- 建议：
  如果设计目标是允许缺省控制项，则应将“查不到 key”视为 `match = FALSE`，而不是流程级错误。
- 涉及位置：
  - `src/spmci/spm_ctrl_item.c:38-45`
  - `src/ltsensor/spm_sensor.c:166-171`
- 优先级：高

## 4. `src/ltsensor/spm_sensor.c`

### 总体判断

这个文件本质上是 SPM 传感器框架的分发表。现在的问题不在“功能做不到”，而在于版本分派、数组位置依赖和统一包装函数都偏硬编码，扩展一代新硬件时维护成本会明显上升。

### 优化建议

#### 4.1 用“基础表 + 差异覆盖”替代两张大数组

- 问题：
  `g_spmSensorFuncSetV3` 和 `g_spmSensorFuncSetV5` 的大部分项相同，只在 APD、部分 EC 和 merge EC 上有差异。
- 影响：
  每次新增或调整某个传感器分派逻辑，都要同时检查两张长表，容易漏改。
- 建议：
  先定义一张基础表，再对 V5 做差异覆盖；或者改成按 `sensorId` 显式声明的描述表，而不是依赖数组位置。
- 涉及位置：
  - `src/ltsensor/spm_sensor.c:47-145`
- 优先级：高

#### 4.2 抽出统一分派辅助函数，减少包装函数重复

- 问题：
  `SPM_OpenSensor()`、`SPM_CloseSensor()`、`SPM_GetSensorCfgData()`、`SPM_SetSensorCfgData()`、`SPM_ReadSensorData()`、`SPM_ReadMiscSensorData()`、中断注册/注销函数都在重复做同样的边界校验和空指针判定。
- 影响：
  这类重复逻辑会让错误码、日志格式和 `LTR_UNLIKELY` 使用逐步漂移。
- 建议：
  抽出统一的分派/校验辅助层，把差异限制在函数签名本身。
- 涉及位置：
  - `src/ltsensor/spm_sensor.c:213-359`
- 优先级：中

#### 4.3 清理初始化路径中的小型样板问题

- 问题：
  `SPM_LTSensor_Init()` 中 `SUBSYS_SetSysName("SPM")` 被调用了两次。
- 影响：
  虽然问题不大，但会增加阅读噪音，也提示初始化流程缺少收敛。
- 建议：
  保留一次明确的注册调用，并把初始化步骤组织成固定顺序。
- 涉及位置：
  - `src/ltsensor/spm_sensor.c:183-210`
- 优先级：低

### 潜在缺陷风险

#### 4.4 当前分发表强依赖“数组下标 == sensorId 偏移”

- 问题：
  两张 `Sensor_OperateFuncSet` 表大量使用位置索引和 `NULL` 占位，一旦 `sensorId` 枚举顺序变化，或者中间插入新传感器，极易出现静默错位。
- 影响：
  这类错误往往编译期无法发现，只能在运行时由错误路由暴露出来。
- 建议：
  改用显式 `sensorId -> function set` 描述表，或至少使用带注释的指定初始化方式，降低位置耦合。
- 涉及位置：
  - `src/ltsensor/spm_sensor.c:47-145`
- 优先级：高

#### 4.5 未识别版本时默认回落到 V3，扩展新版本时有误路由风险

- 问题：
  `g_SensorFuncSetMap` 最后一项把“未匹配任何条件”的情况默认映射到 `g_spmSensorFuncSetV3`。
- 影响：
  当未来增加新的 OEB 版本但控制项未同步更新时，系统可能静默落到 V3 路径，而不是显式报错。
- 建议：
  对未知版本增加告警或显式失败，再由上层决定是否允许 fallback。
- 涉及位置：
  - `src/ltsensor/spm_sensor.c:155-180`
- 优先级：中

## 建议的落地顺序

1. 先处理高优先级风险项：
   - dual APD 的左右侧设备映射核对
   - `g_wsecConfigPg` 全局状态下沉
   - `SPM_SensorCheckCI()` 的默认兜底策略
   - `memcpy_s()` 返回值检查
2. 再做结构性收敛：
   - APD 普通版 / dual 版共享骨架
   - EC 标定下发公共流程
   - `spm_sensor.c` 的版本分发表降重
3. 最后补测试：
   - APD/EC 的纯计算函数单测
   - EEPROM 数据边界测试
   - 版本控制项缺省/未知值测试
